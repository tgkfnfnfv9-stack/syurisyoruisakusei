# PDF／JSON出力の検証記録

## 検証の範囲

APIを模擬した自動テストとコードの独立レビューを実施しました。以下の時間は **API模擬条件下の制御待ち時間** であり、携帯・PC実機のPDF描画速度ではありません。

実ブラウザ起動を試みましたが、本実行環境ではChromiumが `SIGTRAP` で終了したため、実際のPDF画像生成・ネイティブ保存／共有操作・PDFの目視比較は未確認です。

## 再現方法

```bash
node --test tests/*.test.cjs
node tests/validate-drive-integration.cjs
node tests/export-benchmark.cjs
# 全測定値をJSONで保存する場合
node tests/export-benchmark.cjs --json > docs/export-benchmark-results.json
```

比較には旧コミット `1cf9131` を含むGit履歴が必要です。旧版の報告書・見積書HTMLから実際のPDF生成、同時出力、JSON出力関数を読み込み、新版の `document-export.js` と同じブラウザAPI模擬環境で実行します。旧版の処理を別実装で再現する方式ではありません。

テストとベンチマークは `tests/helpers/export-fixture.cjs` を共有します。回帰テストは長いタイムアウトを短縮しますが、ベンチマークは `realTimers: true` を指定し、実時間のタイマーを使用します。

## 待ち時間の測定条件

- 測定日時：2026-10-07T11:24:41.522Z（UTC）。
- 環境：Node.js v24.19.0、linux/x64。
- 各条件3回、中央値。報告書・見積書とも1ページ、同じ固定入力データ。
- `html2canvas` は1ページにつき実時間20ms後に固定キャンバスを返す模擬関数。jsPDF・DOM・署名準備・保存APIも模擬。
- 条件A：`whenIdle()` が呼ばれるたびに実時間250ms待つ。
- 条件B：`whenIdle()` が未解決のPromiseを返す。100ms観測して未完了かを判定。
- PDF単独・同時出力はファイル生成まで、JSON単独はJSON準備までを比較。新版は保存・共有ダイアログの準備完了までを含む。
- 共有先選択、保存ダイアログでの操作、ディスク書込、実画像描画、通信の実測は含まない。
- 旧版同時出力の1.2秒後の連続ダウンロード待機は、この生成完了比較には含まない。

**条件Aは重複呼出しを見えるようにするため、2回目の `whenIdle()` にも250msを課しています。実環境では最初の待機で保存が完了すれば2回目がすぐ解決するため、同時出力が常に2倍の通信待ちになるという意味ではありません。**

### 条件A：呼出しごとに250msの自動保存待機

| 書類 | 出力 | 修正前・中央値 | 修正後・中央値 | `whenIdle()` 回数・前→後 | PDF描画回数・前→後 |
|---|---|---:|---:|---:|---:|
| 報告書 | PDF単独 | 271.39 ms | 20.80 ms | 1→0 | 1→1 |
| 報告書 | JSON単独 | 250.66 ms | 0.16 ms | 1→0 | 0→0 |
| 報告書 | PDF＋JSON | 521.78 ms | 20.57 ms | 2→0 | 1→1 |
| 見積書 | PDF単独 | 270.94 ms | 20.67 ms | 1→0 | 1→1 |
| 見積書 | JSON単独 | 250.83 ms | 0.16 ms | 1→0 | 0→0 |
| 見積書 | PDF＋JSON | 521.52 ms | 20.53 ms | 2→0 | 1→1 |

新版は通信待機を呼ばず、PDFの模擬描画20msが主な待ち時間になっています。PDF自体の描画回数は旧版も1回であり、主因を「PDFが二重生成されていた」とは結論していません。旧版はプレビュー描画内の調整と生成直前の調整が重複し、JSON単独もプレビューを再描画していました。

### 条件B：自動保存が完了しない

| 書類 | 出力 | 修正前 | 修正後・中央値 |
|---|---|---|---:|
| 報告書 | PDF単独 | 100ms観測で未完了 | 20.58 ms・完了 |
| 報告書 | JSON単独 | 100ms観測で未完了 | 0.14 ms・完了 |
| 報告書 | PDF＋JSON | 100ms観測で未完了 | 20.50 ms・完了 |

旧版は最初の `whenIdle()` で停止しPDF描画にも進みません。新版は同じ未解決の自動保存APIが存在しても呼び出さずに完了しました。これは通信不良時の制御経路を検証するもので、実際の回線・Drive障害を発生させた試験ではありません。

## 自動テストと独立レビュー

新規 `tests/document-export.test.cjs`：20件成功。

| 確認内容 | 方法・結果 |
|---|---|
| PC／携帯のPDF・JSON・両方 | API模擬で全6通り。生成済みファイルへの個別取得経路を確認 |
| PDFとJSONの同時点整合 | 生成中に元データと2ページの元DOMを書き換え、両出力が元の内容を保持することを確認 |
| ファイル名の整合 | PDF・JSONとも同じ保存開始時の名前を保持 |
| 二重実行 | PDF処理中の再クリックで採取・描画が増えない |
| 共有非対応 | 一括共有できない場合もPDF・JSON両方の個別保存を提供 |
| 共有のキャンセル・再試行 | ファイルを保持しPDFを再生成せずに再共有 |
| PC保存先選択のキャンセル | 同じ生成済みJSONから再試行 |
| フォルダー保存の部分失敗 | 保存済み件数を明示し、失敗した書込をabort、個別取得を維持 |
| 中止・生成エラー | 一時ページとダイアログを片付け、入力ロックを解除して再実行 |
| 画像欠落・署名準備失敗 | 画像を黙って省略せず明示的に失敗 |
| PDF生成停止・署名待機停止 | タイムアウトと後始末を確認 |
| iframeの独立性 | 既存IDを保持しつつメイン画面のセレクターを汚染しない。標準doctypeと続紙の `#sheetExtra` 文脈も保持 |
| オブジェクトURL | ダイアログ終了時に解放 |
| ズーム | 既存15件のホイール・ピンチ・倍率範囲・複製だけの原寸化テストを維持 |

既存の入力・計算・読込・自動保存・署名・値検証テストも確認しています。JSONの構造・同時点整合は自動テスト済みですが、ダウンロードした実ファイルを実ブラウザで再読込し、実PDFと目視で突き合わせる確認は未実施です。

## 残る確認事項

- iPhone Safari／Android Chrome／PCブラウザでの実際の複数ファイル共有、保存先選択、共有先アプリによる両ファイル受取。
- 実PDFのサイン・画像・日本語文字・金額・複数ページと、再読込したJSONの目視照合。
- プレビュー倍率20％／100％／400％で出したPDFの画像・寸法の一致。
- マウスホイールと実機2本指の操作、保存直後のダイアログ終了。
- 実機の処理速度、実回線の通信不良下での出力速度。

実ブラウザが利用可能になった場合は、端末・OS・ブラウザ版、入力内容、ページ数・画像条件、倍率、各3回の生成完了時間、保存先と結果をこの記録に追記してください。
